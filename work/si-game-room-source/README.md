# 缘缘庄牌桌 · 本地验收版

祀在 QQ 群和微信群为群友开桌。玩家用同一条邀请链接进入手机网页，群里只收到开桌邀请和整桌最终结算。每个群在每个机器人账号下有独立的一桌。第一位入座者是桌主，其他玩家在网页申请，桌主通过后开局。

| 群命令 | 玩法 |
| --- | --- |
| `/德州 开桌` | 2–8 人，五手，无限注德州扑克，使用局内筹码 |
| `/川麻 开桌` | 四人血战到底，支持换三张、定缺、碰杠、抢杠和一炮多响，使用基础计分 |
| `/三国杀 开桌` | 桌主在大厅选择桌型和武将扩展 |

## 三国杀桌型

| 桌型 | 人数 |

| 身份场 | 4–8 人，含经典五人和八人配置 |
| 1v1 | 2 人 |

| 斗地主 | 3 人，竞价选地主，地主对两名农民 |
| 承天之弈实体规则验收 | 2 人，从已核对技能的实体牌构筑四十张军营，主帅体力归零结算 |
| 3v3 血战到底 | 6 人，随机座次，每席五选一并荐两将，两队主帅各定三名备将，先击破四名敌将的一队取胜 |

承天之弈的公共牌来自游卡公布的 104 张实体牌表，每种花色、点数各两张。走马换将用实际锦囊结算，将旧将送到军营底，再上阵一将，换自己的将另摸一张。新版乐不思蜀锁定单个对方武将，非红桃判定继续留在判定区。坐骑共用一个位置，增加一点手牌上限。[官方公共牌表公告](https://www.sohu.com/a/1045302182_121124836) · [牌表及实体牌面](https://q9.itc.cn/q_70/images03/20260703/fe7888cc91c541a48df08371840e6901.png)

新版从空军营编排，先收录一张同名起始武将。四个势力各接入一张主帅牌，已接入结算的 24 张武将来自首弹官方图鉴。可以逐张增减，也可以用当前已实现的卡牌快速补足四十张。构筑验收覆盖单势力／双势力和十张副势力限制。同版卡张数限制、赛事后援、助阵突破、完整 FAQ 及其余武将技能仍待接入，快速补足的军营不用于判断赛事构筑合法性。[官方图鉴](https://i.sanguoshacard.com/) · [官方规则手册入口说明](https://www.sohu.com/a/1048096283_121124836)

经典牌组采用 104 张标准牌、4 张 EX 牌和 52 张军争牌，保留各牌的花色、点数和张数。大厅可勾选风、火、林、山、神将扩展，共 40 张扩展武将牌。本轮补入天香、鬼道、驱虎、放逐、巧变、武魂、归心、多牌龙魂、极略与连破等技能。点按手牌可查看牌面和可执行操作。兼容范围列在邓艾、左慈等对应的武将说明里。[经典血战到底规则](https://www.sanguosha.com/act/20140228/index.html)

## 运行

Ubuntu 安装、手机 HTTPS 及验收命令见[项目部署手册](../../README.md)。独立启动时在本目录运行 `python server.py --help`。

## 邀请、席位和结算

只有从有效邀请进入才能拿到浏览器通行凭据。链接有效期为八小时。复制进入后的牌桌地址给其他设备时，对方仍需原邀请。邀请可被转发，入座由桌主在网页确认。手牌、暗杠和隐藏身份由服务端按浏览器席位隔离。

牌局和结算存在本地 SQLite 中。刷新页面可回到原座位，换浏览器或清除站点数据会生成新席位。大厅提供「取消申请」和「离开大厅」，桌主离开会立即交接给在线的已入座玩家，没有已入座玩家时由最早到访的在线申请者接任。大厅断线超过 90 秒会释放座位或申请，并按相同顺序交接桌主；回来后可重新申请。若没有接任者，下一位入座者成为桌主。无人在线超过 90 秒的大厅允许原群重新开桌。

已开局的离线玩家保留原席位、手牌和身份，可在原浏览器回来继续。桌主断线超过 90 秒时只将管理权交给在线的已入座玩家，接任者可以结束卡住的牌局。桌主也可以散桌以便原群重新开桌。完成对局的最终战报由机器人通过仅监听本机的桥接接口读取，发送到开桌的原群。

## 网页就绪与发布

规则模块在服务接受邀请前加载。公网 `/ready` 检查网页入口、脚本和样式是否齐备，祀在创建牌桌前从玩家使用的 HTTPS 源检查就绪状态，失败时有限重试，未就绪时不创建牌桌。首页自动重试脚本和样式加载，牌桌请求遇到临时代理错误时继续重连；只有带有 `room_error` 标记的席位或邀请错误才终止重连。

Ubuntu 的小游戏使用本目录的 `deploy.py` 单独发布。脚本参照祀的候选验证、备份、切换和恢复流程：只打包游戏 Python 模块、README 和网页资源，包含 `.webp`；不把源码中的 `.runtime`、测试、部署工具或历史部署记录混入运行版。先发布小游戏，再发布引用 `/ready` 的祀插件。启动时会为已有数据库补充在线时间字段并给予 90 秒宽限。管理员需在发布后用原群邀请核查首次加载、离开大厅、断线交接及重新开桌。

在宿主机使用小游戏现有的 Python 环境执行：

```bash
/srv/sibot/venv/bin/python -B /srv/sibot/work/si-game-room-source/deploy.py --check
sudo /srv/sibot/venv/bin/python -B /srv/sibot/work/si-game-room-source/deploy.py --deploy
```

`--check` 在独立候选目录和临时数据库中试验三种游戏的离桌／接管、旧库迁移、原群重新开桌，以及随机回环端口上的邀请、Cookie、首页／CSP、脚本、样式和首次入座。它不调用 QQ／微信接口或发送群消息。端口被限制时，可用 `--store-check` 单独验证数据库事务，但该结果不能代替 HTTP 或部署验证。

`--deploy` 先取得运行目录 `.runtime/.deploy.lock`，核对 `sibot-game.service` 的工作目录和运行状态，再验证候选；通过后停服，将原代码和完整 `.runtime`（含 SQLite 主库、WAL／SHM、桥接配置和证书）备份到源码目录 `.deployments/时间编号/previous`，切换应用文件并重启原服务。它保留现有 systemd 配置、端口和域名，检查本机与公网 `/ready`、脚本／样式摘要以及本机桥接；失败时停服恢复代码与运行数据，再验证原版。上线探测使用有总时限的子进程，防止 DNS 后台线程拖住退出。部署阶段、结果和检查日志保存在同次 `.deployments` 目录的 `result.json` 和 `*-check*.log`；备份含运行凭据，应保留目录原有访问权限。

Ubuntu 的 /反馈 部署 已通过独立宿主 root 服务 sibot-deploy 接入小游戏。统一发布先更新小游戏 /ready 与网页资源，再更新依赖它的祀插件；发生失败时恢复该批代码和运行数据。停止小游戏会连带停止 HTTPS 反代，发布服务会依次启动 sibot-game 与 sibot-game-https。工单内的 Codex 按本轮授权修改源码和静态核对，部署由管理员确认后的统一入口执行。
